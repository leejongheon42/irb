# 서류 점검 파이프라인 작업 계획 (VELIVO CATCHER)

작성일: 2026-11-14 · 대상 코드: `irb_automation/qc` (+ `engine`, `package`, `web`)
기준 문서: Notion 「VELIVO CATCHER Pipeline Brainstorming」(규칙 정의 개정 2026-11-12, 조회 2026-11-14)

이 문서는 LLM 코딩 에이전트가 **이 파일만 읽고 순서대로 구현**할 수 있게 쓴 실행 계획이다.
규칙의 판단 기준(M01~M10, E01~E10의 플래그·예외·등급)은 9장에 옮겨 두었으므로 Notion에 접근하지 않아도 된다.

## 0. 실행 에이전트가 먼저 읽을 것

### 0.1 작업 방식

1. 5장의 작업(T-xx)을 **번호 순서대로** 하나씩 수행한다. 한 작업 = 한 커밋. 의존성은 6장 표를 따른다.
2. 작업을 시작하기 전에 그 작업의 "변경 파일"을 실제로 읽는다. 이 문서의 코드 설명은 2026-11-14 기준이며 달라졌을 수 있다.
3. 각 작업은 "완료 기준"의 테스트가 통과해야 끝난 것이다. 테스트를 먼저 쓰고 구현한다.
4. 작업을 마치면 이 파일 10장 진행표의 해당 줄을 `[x]`로 바꾸고, 계획과 다르게 구현한 점을 한 줄로 적는다.
5. 7장 "결정 필요 사항"에 걸리는 부분은 **표의 기본값으로 구현**하고 멈추지 않는다. 값은 YAML 설정으로 빼서 나중에 바꿀 수 있게 한다.

## 1. 목표와 범위

### 1.1 파이프라인

```
문서 업로드 → 스캔 → 검증 → 결과 확인 → 수정 → 다운로드      (재검증 없는 단일 파이프라인이 기본)

검증 = ① 제출 서류 필수 서류 검사        (E10 + 신청 경로별 필요 서류)
       ② 서류별 문서 일치성 및 규격 검사   (M01~M10, E01~E09)
       ③ 점수·판정                        (100 − 15C − 7M − 2m, QC 상태 5종)
```

- ①, ②는 사용자가 지정한 단계다. **③은 요청 문장이 "3."에서 끊겨 있어 Notion의 "규칙 1 & 2 → 점수 체계 → Pass/Fail"로 채웠다**(7장 D0).
- 검토 단위: PI가 **같은 IRB 신청에 함께 제출할 예정이라고 지정한 문서 묶음**. 대상 문서는 연구계획서, 신청서(또는 e-IRB 입력 내보내기), 설명문·동의서, 면제 근거, 모집문서, 설문지·증례기록서, 연구 서약서, 추가 서류(외부 인력 협약서, 이해상충공개서 등).
- 1차 대상 기관: **공용 IRB(공용기관생명윤리위원회)**. 병원 자체 IRB용 기존 기준은 유지한다.

### 1.2 범위 밖

- 이전 제출본·승인본과의 변경 비교(R11).
- 누락 내용을 AI가 대신 써 넣는 보완본 작성(기존 `서류점검_고도화_계획.md`의 W11~W13). 이 계획이 끝난 뒤 별도 진행.
- "규칙 2: IRB 평가점검표". Notion에 항목이 정의되어 있지 않다. 규칙 레지스트리에 `source: irb_checklist` 자리를 만들어 두기만 한다(T-03).
- 법령 적합성의 확정 판정. 적용 조항·서식·버전이 연결되지 않은 규정 지적은 감점하지 않는다.

### 1.3 기존 계획 문서와의 관계

`docs/서류점검_고도화_계획.md`(2026-11-10)와 충돌하면 **이 문서가 우선**한다.

| 주제 | 고도화 계획 | 이 계획(Notion 기준) |
|---|---|---|
| 점수 | 영역별 배점(35/25/20/10/10), `READY/REVISE/HOLD` | 단일 식 `100 − 15C − 7M − 2m`, QC 상태 5종(8장) |
| 필수 서류 누락 | Critical 이슈 | `확인 필요`(HOLD). 감점 없음 |
| 교차 대조 기준값 | 과제 입력값 → 계획서 → 다수결 | 추정 금지, PI가 선택 |
| 감점 대상 | 규칙 지적 전부 + 인용 확인된 AI 지적 | 검토자가 확정한 고유 오류만 |

고도화 계획의 W1~W4(평가 도구·필수 항목 판정·사실 추출·AI 인용 검증)는 이미 일부 구현되어 있고 그대로 활용한다.

## 2. 현재 코드 상태 (2026-11-14, 작업 트리 기준)

미커밋 변경이 있다(`qc/required.py`, `structure.py`, `scoring.py`, `eval.py`, `tests/test_qc_reliability.py` 등). **T-00에서 먼저 테스트를 돌려 기준선을 확인하고 커밋한다.**

### 2.1 실행 흐름

```
service.run_uploads() / run_for_protocol()
  → service._read_doc()                 텍스트 추출(+DOCX 머리글·바닥글), doc_type은 submission.guess로 추정
  → service.run()
      → checks.run_rules(docs, protocol)   → (phase1, phase3)
            facts.extract(text)            정규식 10종 → Fact(key, value, raw, line)
            required.check_required()      절 단위 필수 기재사항(met/partial/missing)
            check_version / check_placeholders / check_pii / check_regulatory
            check_terminology / cross_check          ← 문서 간·과제 정보 대조
            check_typos / check_numbers              ← phase 3
      → ai_phase.run_ai()                  1회 호출, evidence 인용 검증(confidence=ai_verified|ai_unverified)
      → scoring.score(issues)              100−15C−7M−2m, <80 또는 Critical≥1 → FAIL
      → QCRun 저장(issues, docs, counts, phases, verdict)
  → service.apply_fixes() → autofix.apply()   문자열 치환(DOCX 변경 추적본·수정 완료본, HWPX)
```

## 4. 공통 설계 (모든 작업이 따르는 계약)

### 4.1 신청 경로 프로필 `profile`

`QCRun.profile`(JSON 컬럼 신규). 과제가 없어도 만들 수 있어야 한다.

```python
{
  "committee": "public_irb" | "institution",          # 기본 public_irb
  "study_type": "human" | "specimen" | "both" | "unknown",
  "application": "new" | "exemption",                 # 신규심의 / 심의면제
  "data_source": ["collect", "existing_internal", "external", "public", "bank"],   # 복수
  "consent": ["obtain", "waiver_request", "existing_consent", "not_applicable"],   # 대상군·활동별로 복수 가능
  "method": ["survey", "intervention", "records", "specimen", "stem_cell"],        # 계획서 서식 선택에 사용
  "drug": bool,            # 약물 투여 있음 → M02·M03 적용
  "visits": bool,          # 방문 일정 있음 → M04 적용
  "vulnerable": ["children", "proxy"],
  "multicenter": bool, "external_transfer": bool, "student_pi": bool,
  "source": {"<필드>": "user" | "record" | "doc" | "default"}      # 값의 출처
}
```

- 우선순위: 사용자 답변 > 과제 레코드 > 문서에서 규칙으로 읽은 값 > 기본값(`unknown`).
- **심의면제(`application=exemption`)와 서면동의면제(`consent=waiver_request`)는 별도 변수다.** 섞지 않는다.
- `unknown`인 필드에 의존하는 규칙은 `해당 없음`이 아니라 `확인 필요`(사유: "적용 여부 미확정")로 기록한다.
- `profile_conditions(profile) -> set[str]`가 기존 `conditions()`와 같은 문자열 집합을 반환하고, 새 조건(`human, specimen, new, exemption, collect, existing, survey, intervention, drug, visits, proxy, multicenter, student_pi`)을 추가한다.

### 4.2 검사 단위 `checks`와 판정 상태

`QCRun.checks`(JSON 컬럼 신규). **검사 단위 = 규칙 × 필드 × 비교 범위.** 이슈가 없는 "일치"와 "해당 없음"도 여기에 남는다.

```python
{"rule": "M05", "field": "individual_period", "scope": "전체 대상군",
 "docs": ["d1", "d2"], "result": "match|mismatch|missing|needs_check|na",
 "reason": "",            # na·needs_check는 사유 필수
 "issue": 7 | None}       # 연결된 이슈 id
```

| result | 화면 표기 | 이슈 생성 | 감점 |
|---|---|---|---|
| `match` | 일치 | 없음 | 없음 |
| `mismatch` | 불일치 | 있음(후보) | 확정 후 |
| `missing` | 필수내용 누락 | 있음(후보) | 확정 후 |
| `needs_check` | 확인 필요 | 있음(질문 포함) | 없음. 미완료로 표시 |
| `na` | 해당 없음 | 없음 | 없음. 사유 기록 |

`needs_check` 사유 코드(enum): `file_missing`(파일 미제공), `unreadable`(추출 실패), `scope_unclear`(범위 불명확), `basis_unverified`(적용 근거 미확인), `applicability_unknown`(적용 여부 미확정), `alias_unknown`(별칭 관계 미확인), `review_pending`(사람 검토 대기).

### 4.3 이슈 dict에 추가하는 선택 키

```python
"rule_id": "M03",                         # M01~M10, E01~E10, R00(과제 입력값 대조)
"flags": ["용량 불일치", "빈도 불일치"],    # 주 플래그가 [0]. rules.yaml의 플래그 이름과 정확히 일치
"rule_source": "mira_public|velivo|public_irb|record",
"rule_version": "2026.11.12",
"result": "mismatch|missing|needs_check",
"reason": "scope_unclear",                # needs_check일 때
"scope": {"arm": "", "site": "", "activity": "", "period_kind": "", "label": "시험군 · 1회 투여"},
"within": "doc|cross",                    # 문서 내 모순 / 문서 간 모순
"locations": [{"doc": "d1", "section": "3.2", "quote": "…", "value": "100mg", "norm": "100 mg"}],
"proposed_severity": "critical",          # 규칙이 제안한 등급. "severity"는 현재 유효 등급
"review": "candidate|confirmed|dismissed|accepted|resolved",
"review_note": "", "reviewed_by": 3, "reviewed_at": "2026-11-14T10:20",
"question": "두 문서 중 어느 값이 맞습니까?",   # PI에게 묻는 확인 질문
"targets": ["d2"],                        # 수정할 문서(기준값 확정 전에는 빈 목록)
"group": "M03|dosage|시험군",             # 묶음 키(R3). 같은 group은 1건으로 집계
"advice": True,                           # 개선 의견(비감점). severity는 "minor"로 두되 집계에서 제외
```

- 기존 키 `status`는 필수 항목 판정용으로 유지한다. `status == "unchecked"`는 `result == "needs_check"`와 동일하게 취급한다.
- `confidence`(rule / ai_verified / ai_unverified)는 **확신도**이고 `severity`와 독립이다(R6).
- `locations`는 최소 원문 인용 + 정규화 값. 누락 이슈는 `locations` 대신 `basis`(요구 근거)와 `checked`(검사한 문서·절 목록)를 채운다.

### 4.4 규칙 레지스트리 `qc/rules.yaml` (신규)

```yaml
version: "2026.11.12"
rules:
  M03:
    label: "용량·횟수·경로"
    source: mira_public            # mira_public | velivo | public_irb | irb_checklist
    applies_when: [drug]           # profile_conditions와 교집합이 있어야 적용. 비면 항상 적용
    doc_roles: [protocol, consent_form]
    flags:
      "용량 불일치":   {severity: critical, source: mira_public}
      "빈도 불일치":   {severity: critical, source: velivo}
      "경로 불일치":   {severity: critical, source: velivo}
      "투여단계 불일치": {severity: major, escalate: critical}
      "투여정보 누락":  {severity: major, escalate: critical, merge_with: M06}
      "용량–총량 모순": {severity: major, escalate: critical}
    owner: ""
```

- 9장의 표를 그대로 옮긴다. `escalate`는 "검토자가 올릴 수 있는 상한"이며 자동으로 올리지 않는다.
- `severity: null`인 플래그(예: M10 설명 불명확)는 개선 의견(`advice: true`)으로만 낸다.
- `merge_with`는 같은 원인일 때 흡수될 소관 규칙이다(T-20의 묶기에서 사용).
- 로더: `qc/rules.py`의 `rules() -> dict`, `flag_meta(rule_id, flag) -> dict`. `criteria()`와 같은 mtime 캐시 방식.
- `QCRun.criteria_version`에 `criteria.yaml` 버전과 `rules.yaml` 버전을 `"2026.11.11+r2026.11.12"`처럼 함께 기록한다(String(32) 이내).

### Phase B. ① 제출 서류 필수 서류 검사

#### T-04 필요 서류 기준표 `qc/required_docs.yaml`
- 목적: 신청 경로별로 묶음에 있어야 할 문서를 정의한다.
- 입력 자료: `docs/reference/공용IRB/98개_시나리오별_제출서류.md`(공통 A, 1장 선택표, 2장 서식 밖 자료)와 `완결_경로_시나리오.txt`. **3장의 시나리오 1~98을 전부 옮기지 않는다.** 공통 A + 1장 + 2장을 조건식으로 옮기고, 시나리오는 T-06의 테스트 사례로 쓴다.
- 구현(스키마):
  ```yaml
  version: "2026.11.14"
  committee: public_irb
  documents:
    - {doc: protocol, level: required, when: [], form: {survey: "권고 제39호", intervention: "권고 제38호", records: "권고 제43호", specimen: "권고 제40호", stem_cell: "권고 제41호"}, basis: "표준운영지침 제21조"}
    - {doc: consent_form, level: required, when: [obtain], form: {human: "권고 제44호", specimen: "권고 제45호"}}
    - {doc: assent_form, level: conditional, when: [children], note: "만 7~12세. 대리인 동의를 대체하지 않음"}
    - {doc: waiver_request, level: required, when: [waiver_request], channel: eirb_or_file}
    - {doc: exemption_request, level: required, when: [exemption], channel: eirb_or_file}
    - {doc: questionnaire, level: required, when: [survey]}
    - {doc: crf, level: conditional, when: [intervention]}
    - {doc: recruitment, level: conditional, when: [collect], note: "실제 사용하는 모집 문서가 있을 때"}
    - {doc: training_cert, level: required, when: [new]}
    - {doc: coi, level: eirb_input, when: [new]}
    - {doc: pledge, level: eirb_input, when: []}
    - {doc: advisor_pledge, level: required, when: [student_pi]}
    - {doc: mta, level: evidence, when: [specimen, external]}
    - {doc: transfer_agreement, level: evidence, when: [external]}
    - {doc: external_irb_approval, level: evidence, when: [external]}
    - {doc: site_agreement, level: evidence, when: [multicenter]}
  ```
  - `level`: `required`(없으면 `needs_check: file_missing`) / `conditional`(조건이 맞고 본문이 그 문서를 언급하면 `needs_check`) / `evidence`(안내만, 검사 단위 없음) / `eirb_input`(e-IRB 입력 항목. 파일을 요구하지 않고 체크 안내만).
  - `when`은 모두 충족(AND). 위 목록은 초안이며 **참고 자료 원문을 읽고 보정**한다. 참고 자료에 없는 서류·서식 번호·조문을 추가하지 않는다(R7).
  - `institution` 위원회일 때는 기존 `default_ruleset.yaml: required_documents`를 그대로 쓴다(`engine/checklist.build_checklist` 재사용).
- 변경 파일: `qc/required_docs.yaml`, `rules/default_ruleset.yaml`의 `document_types` 카탈로그(없는 종류 추가: `assent_form, questionnaire, recruitment, pledge, advisor_pledge, mta, site_agreement, external_staff_agreement`), `docproc/classify.py`·`submission/guess.py`의 키워드.
- 테스트: YAML 로드, `when`의 조건명이 모두 `profile_conditions`가 만들 수 있는 이름인지 검증.
- 완료 기준: 새 문서 종류가 파일명·본문으로 분류됨(종류별 합성 문서 1건씩).

#### T-05 제출 묶음 구성 검사 (E10) `qc/bundle.py`
- 목적: 묶음에 필요한 문서가 있는지, 역할이 겹치는 파일이 없는지, 다른 연구 문서가 섞이지 않았는지 본다.
- 구현 `check_bundle(docs, profile, rec) -> list[issue]` (`rule_id: "E10"`):
  | 상황 | 결과 | 등급 |
  |---|---|---|
  | `level: required` 문서가 묶음에 없음 | `needs_check` / `file_missing`. 질문: "○○을(를) 제출할 예정입니까? (추가 업로드 / e-IRB 입력으로 대체 / 해당 없음)" | 없음(HOLD) |
  | 같은 `doc_type` 파일이 2개 이상 | `needs_check` / `scope_unclear`. 질문: "어느 파일이 제출본입니까?" (대상군·기관별 문서일 수 있으므로 오류로 확정하지 않음) | 없음 |
  | `doc_type == "other"`(분류 실패) | `needs_check`. 문서 종류를 선택하게 함 | 없음 |
  | 제목·연구번호·PI가 다른 문서와 전혀 맞지 않음(E01 값이 모두 불일치) | `mismatch` 후보 "다른 연구 문서 혼입 가능" | Major 제안 |
  | 서면동의면제 경로인데 동의서 없음 | `na`("면제 요청 경로") — **오류 아님** | — |

#### T-22 점수와 QC 상태
- 변경 파일: `qc/scoring.py`, `criteria.yaml: scoring`, `qc/models.py`, `package/service.py`(`qc.critical/major` 참조부), 템플릿.
- 구현(8장의 정의 그대로):
  ```python
  def score(issues, checks) -> dict:
      # 집계 대상 = review == "confirmed" 이고 merged_into 없음, advice 아님
      # 제외 = candidate, dismissed, accepted, resolved, needs_check, ai_unverified
      return {"score": int | None,          # 확정 점수. 입력 없음·범위 미정이면 None(산출 불가)
              "projected": int,             # 예상 점수: 감점 가능한 후보가 모두 확정된다고 가정
              "provisional": bool,          # 미확정 항목(candidate, needs_check)이 있으면 True
              "counts": {"critical", "major", "minor"},              # 확정
              "pending": {"candidate": n, "needs_check": n},
              "coverage": float | None,     # 판정 완료 단위 / 적용 대상 단위(na 제외, needs_check 포함)
              "status": "FAIL|HOLD|REVISE|MINOR|PASS"}
  ```
  - 상태 우선순위: ① 확정 Critical ≥ 1 → `FAIL` ② 미확정(candidate 또는 needs_check) 존재 → `HOLD` ③ Major ≥ 1 → `REVISE`(수정 필요) ④ Minor 잔존 → `MINOR`(경미 수정 또는 검토 대기) ⑤ 그 외 → `PASS`.
  - **`pass_score: 80` 커트라인을 제거**한다(Notion에 없는 기준). `critical_fails`는 유지.
  - `QCRun.verdict`에 상태를 저장(String(8)에 들어감). `passed` 속성은 `verdict == "PASS"` 유지. `QCRun.score`는 확정 점수(산출 불가면 0 저장 + `counts["na"] = True`).
  - 기존 `score(issues) -> (total, verdict, counts)` 시그니처를 쓰는 호출부(`service.run`의 문서별 집계)를 함께 고친다.
  - 화면 문구: PASS 옆에 "문서 검토 완료. IRB 승인·면제 확인을 뜻하지 않습니다."를 항상 표시.
- 테스트(Notion 예시표 그대로): C1 → 85 FAIL / M2+m3 → 80 REVISE / m2 → 96 MINOR, 수용 후 PASS / 확정 0 + 확인 필요 4 → 잠정 100 HOLD / 인원 모순 3문서 → 93 REVISE / 적용 50단위 중 45 완료 → coverage 0.90 / 문서 0건 → 산출 불가 / Minor 60건 확정 → 0점(하한) 이지만 묶기로 실제 건수는 줄어듦.

**점수 = max(0, 100 − 15×Critical − 7×Major − 2×Minor)**

- 감점 대상: 검토자가 확정한 **고유한 미해결** 오류. AI 후보·확인 필요·해당 없음·개선 의견은 감점하지 않는다.
- 미확정 항목이 있으면 **잠정 점수**로 표시한다. 해결된 이슈는 감점에서 빼되 이력을 남기고, 오탐 철회에는 사유를 남긴다.
- 입력이 없거나 검토 범위가 미정이면 100점이 아니라 **산출 불가**.
- 100점 시작·15/7/2·Critical 1건 FAIL은 MIRA 공개 기준 차용. 0점 하한·중복 집계·아래 상태 조건은 Velivo 초안.

| 우선순위 | 조건 | 상태 | `verdict` |
|---|---|---|---|
| 1 | 확정 Critical ≥ 1 | FAIL: 점수와 관계없이 수정 후 재검사 | `FAIL` |
| 2 | Critical 없음 + 필요한 입력/검토/적용 여부 미확정 | HOLD: 검토 보류, 잠정 점수 병기 | `HOLD` |
| 3 | 미확정 없음 + Major ≥ 1 | 수정 필요 | `REVISE` |
| 4 | Critical·Major 없음 + Minor 잔존·수용 판단 미완료 | 경미 수정 또는 검토 대기 | `MINOR` |
| 5 | 검토 완료 + Critical·Major 없음 + Minor 없음 또는 사유와 함께 수용 | QC PASS (IRB 승인·면제 확인을 뜻하지 않음) | `PASS` |

**검토 완료율 = 판정 완료 검사 단위 ÷ 적용 대상 검사 단위.** 확인 필요는 분모에 포함, 해당 없음은 근거 확인 후 제외. 예상 문서 목록의 미제공 입력도 분모에 반영. 분모 미정이면 완료율 미확정.

## 9. 규칙 정의 (rules.yaml로 옮길 원본)

등급 표기: **C** Critical, **M** Major, **m** Minor, `→C` 검토자가 Critical로 올릴 수 있음, `확인` 초기 확인 필요, `의견` 비감점 개선 의견. 출처: ◆ MIRA 공개 예시, 표시 없음 = Velivo 제안.

공통 판정 순서: ① 해당 연구·문서에 적용되는가 → ② 같은 대상·범위·시점인가 → ③ 원문을 충분히 읽었는가 → ④ 양립하지 않는 내용 또는 근거 있는 누락인가 → ⑤ 어떤 플래그인가 → ⑥ 영향·등급·확정 여부 기록.

| E10 제출 묶음 구성 | PI 지정 목록대로 포함됐는지, 필요 문서 누락·같은 역할 파일 중복 | 미제공·지정 불명확은 확인 필요. 잘못 포함 확정 시 M. 문서 종류별 버전은 같을 필요 없음 |

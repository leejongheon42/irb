# Vercel PDF 업로드 장애 검토

2026년 11월 25일 · IRB 서류 심사 · `/mvp`

## 운영에서 확인한 현상

업로드 화면에는 파일당 최대 50MB가 표시됐다. 같은 운영 배포에서 공개 체험 계정으로 18바이트 TXT 한 개를 올렸을 때는 HTTP 200과 `ok`가 돌아왔다. 정상 PDF 한 개(5,403,380바이트)를 올렸을 때는 Vercel이 HTTP 413과 `FUNCTION_PAYLOAD_TOO_LARGE`를 반환했다. 브라우저는 이 응답을 다른 HTTP 오류와 같은 새로고침 안내로 표시했다.

기존 화면은 선택한 파일 전체를 한 번의 multipart 요청으로 전송했다. 이 배포의 Vercel 요청 본문 한도는 기본 4.5MB이고, 앱이 표시하는 50MB는 서버가 받아 검증할 수 있는 **파일 한 개**의 크기다. PDF 한 개만으로도 앞쪽 한도에 걸리면 Python의 PDF 검사까지 도달할 수 없다. 사용자가 처음 선택한 원본의 크기와 당시 응답 코드는 확보하지 못했다. 위 결과는 별도 시험 PDF로 운영 환경에서 재현한 기록이다. [Vercel 요청 크기 제한](https://vercel.com/docs/errors/function_payload_too_large)

## 초기 검토에서 놓친 이유

| 기존 검토 | 확인한 동작 | 빠져 있던 조건 |
| --- | --- | --- |
| `test_five_uploads_persist_and_review_with_consistent_scorecard` | 작은 PDF를 포함한 다섯 파일의 저장과 심사 | 브라우저가 생성한 요청을 Vercel의 실제 한도와 대조하지 않았다. |
| `test_rejected_uploads_cannot_start_review` | 앱의 파일 한도를 1MB로 낮췄을 때 초과 파일이 거부되는지 확인 | FastAPI TestClient가 앱으로 직접 전송하므로 앞단에서 발생하는 413을 거치지 않았다. |
| 업로드 실패 화면 | 비정상 응답을 받으면 실패 문구 표시 | 응답 코드가 보이지 않아 새로고침으로 해결할 수 있는지 판단하기 어려웠다. |

두 테스트 모두 각자 확인하는 동작은 통과한다. 빠진 사례는 **앱이 허용하는 크기이면서 배포 플랫폼의 요청 한도를 넘는 단일 PDF**였다. 기존 수동 검토에서 누가 어떤 파일을 사용했는지는 기록으로 확인할 수 없다.

## 수정과 보호 조치

- 브라우저가 파일을 한 개씩 보내고, 3MiB를 넘는 파일은 최대 3MiB씩 나눠 전송한다. multipart 부가 데이터가 붙어도 각 요청은 Vercel 기본 한도 안에 든다. 일부 파일 전송이 실패해도 이미 성공한 파일은 목록에 남는다.
- 서버는 로그인 사용자와 CSRF 토큰을 확인한다. 전송 식별자를 발급하고 사용자, 원본 이름, 전체 크기, 조각 순서와 실제 바이트 수를 확인한다. 사용자별 전송 기록은 데이터베이스에 보관해 다음 요청이 다른 인스턴스로 가도 이어서 처리할 수 있다.
- 마지막 조각까지 도착하면 원본을 조립하고 기존 PDF 검증 및 저장 절차를 실행한다. 조각 삭제와 업로드 행 저장을 같은 트랜잭션으로 처리한다. 중간 조각은 대기 목록이나 심사 대상에 나타나지 않는다.
- 미완료 전송은 시작 한 시간 뒤 만료된다. 스케줄러가 실행되거나 새 분할 전송이 시작되면 만료된 조각을 삭제한다. 화면은 파일 크기 초과, 로그인 확인 필요, 기타 HTTP 오류를 구분한다.

## 재발 방지 검증

**코드 변경 시** `python -m pytest -q tests/test_mvp.py`를 실행한다. 5MiB 이상의 단일 PDF를 여러 요청으로 전송한 뒤 최종 저장 바이트를 원본과 비교한다. 회귀 테스트에는 다른 계정의 이어 보내기, 마지막 조각의 길이 불일치와 재전송, CSRF 누락, 파일 한도 초과, 만료된 전송 정리도 포함한다.

**배포 확인 시** 다음 절차는 실제 브라우저와 Vercel 운영 도메인에서 수행한다.

1. 개인정보가 없는 합성 PDF를 사용한다. 한 개는 작은 PDF, 다른 하나는 5~6MiB PDF로 준비한다.
2. 업로드 화면에서 파일을 한 개씩 선택한다. 작은 PDF는 일반 업로드 요청 한 번, 큰 PDF는 여러 조각 요청으로 전송되는지 네트워크 기록이나 Vercel 로그에서 확인한다.
3. 두 파일 모두 각각 한 행으로 ‘업로드됨’이 표시되고, 새로고침 후에도 파일명과 바이트 수가 일치해야 한다. 시험에서 생성한 행만 삭제한다.
4. 실패하면 시각, 배포 커밋, 파일 크기, 요청 경로, HTTP 상태와 플랫폼 오류 코드를 기록한다. 원본 서류, 로그인 쿠키, CSRF 토큰은 장애 기록에 첨부하지 않는다.

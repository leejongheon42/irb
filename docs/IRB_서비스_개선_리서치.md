# IRB 서류점검 서비스 개선 제안

2026년 11월 25일 · 연구자용 업로드·채점 화면(MVP)과 과제 관리 기능을 기준으로 조사했다.

**첫 개선으로 점수 옆에 ‘어디까지 검토했는지’를 표시하는 것을 권한다.** 현재 채점 함수에 읽힌 계획서 하나와 본문을 읽지 못한 동의서 하나를 넣으면, 특정 조건에서 100점·통과가 나온다. **첫 추가 기능으로는 ‘수정본으로 다시 점검’을 권한다.** 연구자가 이전 지적을 보면서 고친 파일만 교체하고, 해결된 항목과 남은 항목을 확인하는 흐름이다. 공용위원회가 재심의 때 안내하는 변경대비표와 수정 서류를 준비하는 데도 쓰인다. [현재 채점 코드](../irb_automation/qc/category_scores.py) · [국가생명윤리정책원 공용위원회 심의 안내](https://nibp.kr/page/portal206)

## 개발 우선순위

| 순서 | 개선·추가 기능 | 연구자 또는 운영자가 얻게 되는 것 | 예상 작업량 |
| --- | --- | --- | --- |
| 1 | **검토 범위가 보이는 점수표** | 읽지 못한 파일과 AI가 검토하지 못한 항목을 바로 식별 | 중간. 파일 단위 표시는 작고, 페이지 단위 판독 이력은 추가 개발 |
| 2 | **업로드 시 서류 종류와 신청 조건 정정** | 잘못 분류한 파일을 다시 올리지 않고 적절한 기준으로 점검 | 작음~중간. 기존 선택 UI·조건 처리 재사용 |
| 3 | **수정본 재점검과 변경대비표 초안** | 이전 지적이 어디에서 해결됐는지 확인하고 재제출 자료 준비 | 큼. 점검 회차와 문서 버전의 연결 필요 |
| 4 | **AI 자동 통과 품질 평가** | 자동 통과 정책을 유지하면서 잘못 통과한 사례를 운영자가 발견 | 중간. 전문가가 판정한 평가 자료 필요 |
| 5 | **공식 근거 링크와 서식 판본 관리** | 해당 위원회의 현행 안내로 바로 이동 | 기존 링크 정정은 작음. 변경 감지·검수 연결은 중간 |

우선순위는 결과를 잘못 해석할 가능성, 연구자가 반복하는 작업, 기존 코드의 재사용 가능성을 기준으로 판단했다. 작업량은 상대 추정이다. 4번의 평가 자료 수집과 5번의 링크 정정은 1번과 병행할 수 있다.

## 1. 점수와 검토 범위를 함께 보여준다

**확인한 현상.** MVP는 파일별 본문 인식 여부와 AI 단계 메시지를 이미 표시한다. 다만 채점은 본문이 읽힌 문서를 중심으로 계산한다. 채점 함수에 계획서 100자, 동의서 0자, 동의서에 연결된 ‘확인 필요’ 지적 하나를 넣은 합성 실험에서 결과는 **100점, PASS, 확인 필요 0건**이었다. 채점 함수만 분리한 재현이므로 실제 업로드에서 항상 같은 점수가 나온다는 뜻으로 일반화할 수는 없다. 별도로, 본문 합계가 60만 자를 넘으면 심층 분석은 분할을 시도하지만 최종 AI 재검토는 건너뛴다. [채점 로직](../irb_automation/qc/category_scores.py) · [현재 결과 화면](../irb_automation/web/templates/mvp/review.html) · [AI 심층 분석](../irb_automation/qc/ai_phase.py) · [최종 재검토](../irb_automation/qc/ai_verify.py)

**최소 변경.** 점수 바로 아래에 ‘본문 확인 1/2개 · 동의서 다시 올리기’를 표시한다. AI 검토 대상이 있는 실행에는 ‘최종 재검토 8/10건’처럼 분모를 붙인다. 검토할 후보가 처음부터 0건인 경우와 호출 실패로 처리한 후보가 0건인 경우에는 다른 문구를 쓴다. 점검 범위에 포함한 필수 서류가 판독되지 않으면 전체 결과에는 ‘일부 서류만 점검’을 표시한다. 원문으로 오탐이 확인된 개별 항목은 그대로 통과시킨다.

**완료 기준.** 정상 문서만 있는 묶음, 필수 문서 하나가 안 읽힌 묶음, AI 재검토 일부 실패, 재검토 대상 0건을 각각 시험한다. 처음 화면만 본 연구자가 다시 올릴 파일과 재검토 누락 여부를 맞히는지 확인한다. 페이지 단위 판독률은 빈 표지와 실제 추출 실패를 구분할 수 있을 때 추가한다. [PDF 텍스트 추출과 OCR 처리](../irb_automation/docproc/text.py)

## 2. 연구자가 점검 시작 전에 잘못된 전제를 바로잡게 한다

**현재 흐름.** 업로드 목록에는 ‘추정 서류 종류’와 삭제 버튼이 있다. MVP는 본문을 다시 읽은 뒤 신뢰도가 기준 이상이면 종류를 다시 지정한다. 과제 연결이 없는 점검 프로필은 기본 위원회를 공용 IRB로 두고, 신청 구분 등은 미정에서 시작한다. 반면 과제용 업로드에는 파일별 종류 선택이 있고, 점검 엔진도 사용자 입력을 적용할 수 있다. 공용위원회 공식 안내 역시 신청 구분에 따라 준비 서류를 다르게 제시한다. [MVP 업로드](../irb_automation/web/templates/mvp/upload.html) · [실행 시 재분류](../irb_automation/mvp/service.py) · [과제용 서류 종류 선택](../irb_automation/web/static/submission.js) · [점검 조건 결정](../irb_automation/qc/profile.py) · [공용위원회 신청 유형별 서류](https://nibp.kr/page/portal206)

**최소 변경.** ‘기타’로 분류된 파일 옆에 ‘종류 지정’을 둔다. 나머지 파일도 필요하면 변경하게 하고, 사람이 확정한 종류는 이후 OCR이 끝나도 유지한다. 신청 조건은 점검 결과를 바꾸는 질문만 보여준다. 예를 들어 위원회가 공용인지 기관 자체인지, 동의서를 첨부하는지 또는 면제를 신청하는지를 묻고 ‘모름’도 허용한다.

**완료 기준.** 파일명이 ‘첨부1’인 동의서를 연구자가 정정했을 때 최종 점수표와 적용 기준에 같은 종류가 남아야 한다. 도입 전후에 분류 오류로 인한 재업로드 횟수와 점검 시작까지 걸린 시간을 함께 측정한다. 질문이 늘어 정확도는 올라도 업로드 이탈이 증가할 수 있기 때문이다.

## 3. 수정본을 이전 점검과 연결하고 변경대비표를 만든다

**업무 근거.** 공용위원회는 재심의 시 변경대비표와 보완 요청에 따라 수정한 서류를 안내한다. 강남대학교 IRB는 보완한 부분에 밑줄을 친 계획서와 심의의견 반영 여부 제출서도 명시한다. Stanford eProtocol은 의견마다 답변을 입력하고 신청서의 해당 부분을 수정한 뒤 다시 제출하는 과정을 안내한다. 따라서 기관별 양식을 선택할 수 있게 하되, 공통 데이터는 ‘지적 한 건 ↔ 연구자 답변 ↔ 바뀐 문구와 위치’로 저장하는 편이 유용하다. [공용위원회 재심의 제출자료](https://nibp.kr/page/portal206) · [강남대학교 IRB 제출서류](https://irb.kangnam.ac.kr/menu/04ca9b0652f2fed1346dff71a6e426d1.do) · [Stanford eProtocol 연구자 안내](https://irb.stanford.edu/eprotocol/managing-protocols)

**현재 자산과 추가할 부분.** MVP에는 기존 점검을 재시도하는 기능이 있다. 과제 관리 쪽에는 문서 버전, 본문 줄 비교, 항목별 보완 답변 초안도 있다. MVP에 더할 부분은 연구자가 교체할 원본을 직접 고르고, 원래 점검을 보존한 채 새 회차에서 지적별 결과를 비교하는 흐름이다. 성인용과 보호자용 동의서처럼 종류가 같은 별도 문서를 자동으로 한 파일의 두 버전으로 묶으면 안 된다. [MVP 재시도](../irb_automation/mvp/service.py) · [기존 버전 관리](../irb_automation/submission/versions.py) · [본문 비교](../irb_automation/submission/compare.py) · [보완 답변 초안](../irb_automation/package/revision.py)

**첫 출시 범위.** 점수표에서 ‘수정본으로 다시 점검’을 선택하고 한 파일을 교체한다. 두 회차의 결과를 ‘해결·남음·새 지적·비교 불가’로 보여준다. ‘해결’로 표시하려면 새 본문이 읽혔고 해당 항목이 다시 검토됐어야 한다. 다음 단계에서 연구자가 확정한 행만 ‘보완 의견 / 이전 문구 / 수정 문구 / 문서·위치 / 답변’ 표로 내보낸다. 줄 단위 비교가 어려운 스캔이나 표는 원문을 확인할 수 있게 한다.

**효과 검증.** 같은 보완 요청을 받고 수정본과 변경대비표 초안을 준비하는 데 걸리는 시간, 답변과 실제 수정 위치가 맞지 않는 행 수를 기존 방식과 비교한다.

## 4. AI 자동 통과의 정확도를 별도로 측정한다

현재는 지정 문서의 인용과 판정 이유가 검증되면 Critical도 통과하고, AI와 규칙의 이견을 운영 피드백으로 남길 수 있다. 저장소의 오프라인 평가를 이번 조사에서 실행한 결과, **합성 추출 사례 46개에서 기대 사실 45개를 모두 찾았고, 규칙 판정 사례 15개에서 실패가 없었다.** 이 평가는 사실 추출과 규칙 판정을 측정한다. 실제 AI가 관련 없는 문장을 근거로 잘못 통과시키는 비율은 이 수치에서 알 수 없다. [최종 판정](../irb_automation/qc/ai_verify.py) · [운영 피드백](../irb_automation/qc/feedback.py) · [평가 코드와 측정 범위](../irb_automation/qc/eval.py)

**제안.** 사용자는 검증된 오탐을 즉시 통과한 결과로 받는다. 별도로 운영자는 자동 통과 사례의 표본을 뽑아 원래 지적을 가린 상태에서 전문가가 서류와 기준만으로 판정한 결과와 비교한다. 모집 인원과 최종 분석 인원이 다른 정상 사례, 같은 전체 모집 인원이 실제로 충돌하는 사례를 쌍으로 넣는다. 모델이나 규칙을 바꿀 때 같은 평가 묶음으로 다시 측정한다.

**기록할 지표.** ‘잘못된 자동 통과 비율’은 **검토 표본 중 실제 문제가 남았던 자동 통과 건수 / 전문가가 확인한 자동 통과 건수**로 계산한다. Critical과 기타 등급의 분자·분모를 따로 공개하고, 표본 밖의 결과까지 정확하다고 추정하지 않는다. 충분한 사례가 쌓이면 실제 문제를 계속 지적하는 능력도 함께 평가한다.

## 5. 공식 출처가 바뀌었을 때 관리자가 알 수 있게 한다

**바로 정정할 사례가 있다.** 내장 지식자료의 ‘기관위원회 평가·인증과 연차보고’ 항목은 옛 정보포털 대표 주소를 가리킨다. 국가생명윤리정책원은 해당 포털 서비스를 2026년 3월 31일 종료한다고 공지했다. 현재 옛 주소에 접속하면 목적별 사이트를 고르는 안내가 나온다. 따라서 단순히 링크가 열리는지만 확인하면 개편을 놓친다. 이 항목은 평가·인증 공식 안내에 직접 연결하는 것이 적절하다. [내장 지식자료](../irb_automation/knowledge/builtin/guidelines.yaml) · [정책원 폐쇄 공지](https://nibp.kr/board/notice/post?ntcOid=20000012) · [현재 옛 포털 화면](https://irb.or.kr/) · [평가·인증 공식 안내](https://nibp.kr/page/portal207)

**최소 변경.** 사용 빈도가 높은 안내와 서식부터 기관명, 원문 제목, 연결 주소, 최근 확인일을 저장한다. 주소가 열려도 제목이나 첨부 판본이 바뀌면 관리자에게 검수 대상으로 올린다. 공용 IRB 원문 관리에 이미 있는 검수자·현행판·구판 이력을 재사용한다. 사용자는 적용한 기관과 판본을 보고 원문을 열 수 있어야 한다. [공용 IRB 원문 검수와 판본 관리](../irb_automation/public_irb/sources.py)

## 첫 검증 순서

1. **채점 재현 사례를 회귀 테스트로 고정한다.** 정상 묶음과 일부 판독 실패 묶음에서 사용자가 보게 될 요약을 먼저 정한다. 개별 항목의 통과와 전체 묶음의 점검 범위를 각각 확인한다.
2. **연구자와 연구지원 담당자가 같은 과업을 수행하게 한다.** 기존 화면과 시안에서 ‘읽지 못한 파일 찾기 → 종류 정정 → 수정본 교체 → 보완 답변에 근거 붙이기’를 수행하고, 소요 시간과 잘못된 선택을 기록한다. 순서 효과를 줄이기 위해 화면 제시 순서를 바꾼다.
3. **측정 결과로 다음 투자를 정한다.** 분류 정정이 거의 쓰이지 않으면 질문 수를 줄인다. 수정본 연결이 자주 쓰이고 대비표 작성 시간이 줄면 기관별 내보내기를 확장한다.

조사에는 저장소의 현재 코드·템플릿, 로컬 합성 실험, 국내외 운영기관의 공개 원문을 사용했다. 운영 서버의 배포 버전, 실제 이용 로그, 연구자 인터뷰 자료는 확인하지 않았다. 따라서 제안의 순서는 검증 가능한 개발 가설이며, 절감 시간이나 실제 심의 통과율은 측정한 성과로 제시하지 않았다.
